# 開発・同期の手順
## 1. Work：依頼を整える
最新のSTATUSとコミットを読む→目的を整理→未決定事項を解決→SPEC・DECISIONSを更新→タスクを作成。
ユーザーは「次の改善を進めて」等の自然な指示でよい。AIが文書化を担当する。

## 2. Codex：調査・実装
基準コミットを確認→関連コードを調査→小さい変更単位で実装→必要な検証→状態文書更新→引き継ぎ。
コードの構造が想定と違う場合はタスクを更新する。製品動作を変える大きな判断はWorkへ戻す。

## 3. Work：レビュー
引き継ぎだけでなく対象差分と最新文書も読む。完成条件を満たすか、証拠があるか、未検証が残るかを見る。
GitHubにアクセスできない場合は、対象コミットID付きの差分・最新文書を受け取る。

## 4. 実機
同じコミットから作ったAPKをPixel 7aへ導入。操作手順と期待結果をユーザーへ渡し、実際の結果をVALIDATIONへ記録。
失敗は再現条件を新しいタスクへ落とす。確認待ちは確認済と区別する。

## 同期の約束
- 正式なコード・仕様・状態は https://github.com/moedann/Checkpoint に集める。
- ChatGPTプロジェクトに添付した文書がGitの更新と自動同期するとは仮定しない。
- WorkとCodexの会話履歴が自動共有されるとは仮定しない。
- 接続が使える場合は同じリポジトリ・コミットから読む。接続できない場合はZIP・差分で受け渡す。
- 修正担当を一人にし、別の担当へ渡す時は未コミット差分も明示する。
- 実装担当から戻す情報：タスクID、基準・結果コミット、変更理由、検証結果、残課題。
- コミット未作成時は「未コミット」と明記し、HEADが変更内容を表すと扱わない。

## 完了条件
期待動作が実装され、必要な自動検証が通り、対象に必要な実機確認が通り、文書とコードが一致する。
実機未確認なら「実装済み・実機確認待ち」。環境不足なら「未検証・理由付き」。

## 現在の実行経路（2026-10-12採用）
ユーザーの改善依頼→WorkがGitの最新文書・コードを確認してタスクを具体化→Workがログイン済みCodexのブラウザ画面を操作し、現行クラウド環境Checkpointへ依頼→Codexが調査・実装・検証→Workが結果とGit差分をレビュー→必要に応じてPixel 7a実機確認。

- Linear経由のCodex起動・Triage自動割当は保留。Work–Linear接続と既存課題は保持するが、Codexが起動できるとは扱わない。
- 今回の経路はブラウザ操作。標準のWork→Codex直接API、会話履歴の自動同期、常時自動運転とは扱わない。
- ユーザーが依頼文やZIPを毎回手動で受け渡すことを前提にしない。Workが対象タスク・基準コミット・完成条件・制約を渡す。
- 実行前に対象リポジトリ・環境・ブランチを確認。公開済み環境は準備のスナップショットを持つため、コードが最新とは仮定せず、HEADとGitHubの基準コミットを照合する。
- コードが古い場合は既存変更を保持して通常のGit同期を行う。未コミット差分がある状態でreset/cleanや強制上書きを行わない。
- 一度に一つのタスク、実装担当は一人。WorkはCodexの終了・必要な差分・未検証を確認してから次を判断する。
- ブラウザ認証・接続切れ・利用上限・起動失敗は理由付きで報告し、別途ユーザー操作が必要な箇所だけ案内する。
- 課題を送っただけで実装済みとは扱わない。変更がGitHubへ保存されたか、基準・結果コミットと実際の成功結果を確認する。

### Git接続が利用できない場合
Codex実行環境からGitHubへ接続できない場合、Work側の接続済みGitHub機能で基準コミットの文書・必要なソース・差分を取得し、Codexへ渡す。受領した文書とローカルのコードは区別する。ソースの取得・適用・差分照合を確認してから実装する。GitHubへの保存も実際に成功したコミットを確認し、未保存の作業ツリーだけを正式版として扱わない。
